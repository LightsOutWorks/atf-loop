# devlog.md — FROST HARPOON 開発ログ

日付: 2026-07-29

## 作ったもの

「FROST HARPOON」— `works/seed-006/index.html` 1ファイルで完結する 60 秒のブラウザ FPS 風トイ。

- 氷洞(フロストケイブ)の奥を見上げる固定視点。天井の氷柱(シルエット)と漂う霜の粒子を Canvas 2D で描画
- 画面下中央に固定されたハープーン砲台(ピボット式)から、プレイヤーが指定した方向へ銛(ハープーン)を発射する
- 銛は瞬間ヒットではなく**一定速度で直線飛翔する投射物**で、飛翔中に接触した「ベイパーウィスプ(蒸気の光る精霊)」を**貫通しながら複数まとめてヒット**できる(1発で 2 体以上を捉えると CHAIN ボーナス)
- ウィスプは左右の縁から出現し、ゆるやかな上下の揺れを伴いながら画面を横切って漂う。銛が画面外に出るまでに 1 体も当たらなければ MISS としてコンボがリセットされる
- 操作は「マウス移動で照準、クリックで発射」「タップで即座にその方向へ発射」「矢印キー/ADキーで砲台を回転、Space/Enterで発射」の3系統。砲台は画面下中央に固定されたピボットで、照準は角度(1軸の回転)のみで決まる
- 状態遷移: タイトル → プレイ(60 秒)→ CAVE SECURED → リプレイ
- HUD(スコア / 残り時間 / コンボ倍率)、リザルトに HIT数・CHAIN数・MISS数・LEAK数・ベストスコアを表示
- 効果音は WebAudio のオシレーターによるコード生成音のみ(外部音源なし、♪ボタンとMキーでミュート可)

## テーマ選定理由(既存作品との差別化)

既存5作(ルート NEON RANGE / seed-002 SIGNAL PURGE / seed-003 BEACON WATCH / seed-004 STRATA WARDEN / seed-005 EMBER CANOPY)を精査した上で、判定モデル・入力の自由度・世界観の3軸すべてで意図的に方向転換した。

1. **「瞬間ヒット判定」から「投射物の飛翔ヒット判定」への転換**: 既存5作はすべて、入力(クリック/タップ/確定キー)が発生した瞬間に対象の現在位置と照合して即座に成否が決まる「ヒットスキャン」方式だった(NEON RANGE=画面中心固定の照準、SIGNAL PURGE=移動する照準、BEACON WATCH=対象直接クリック、STRATA WARDEN=グリッドカーソル、EMBER CANOPY=ネットのスイング判定窓)。本作「FROST HARPOON」は発射した銛が**一定速度で実際に画面内を飛び続け、飛翔中の毎フレームで衝突判定を行う**設計にした。発射した瞬間に成否が決まらず、命中は「銛が飛んでいる間、対象がどこにいるか」という未来位置の予測(リード)に依存する——既存5作のいずれにもない遅延ヒット判定を導入した。
2. **「1入力=最大1体」から「1入力=複数貫通ヒット」への転換**: 既存5作はいずれも 1 回の操作で得点対象になり得るのは最大 1 体(NEON RANGE の的、SIGNAL PURGE のバグ、BEACON WATCH の信号灯、STRATA WARDEN の結晶脈、EMBER CANOPY のエンバー)だった。本作の銛は対象を破壊せず貫通するため、**軌道上に複数のウィスプが並んでいれば 1 発で同時に複数ヒットし、CHAIN ボーナスが加算される**。プレイヤーは「今すぐ撃つか」よりも「複数体を貫ける軌道を見極めて撃つか」という新しい戦略軸を持つ。
3. **入力自由度を「2次元の移動・選択」から「1次元の回転」に縮小**: NEON RANGE(yaw/pitch のカメラ回転)、SIGNAL PURGE(2次元移動する照準)、BEACON WATCH(2次元ドラッグ)、STRATA WARDEN(2次元グリッドカーソル)、EMBER CANOPY(2次元の慣性移動するネット)は、いずれもプレイヤー側の操作対象が画面内を2次元的に動く設計だった。本作は発射位置(砲台)を画面下中央に完全固定し、プレイヤーが操作できるのは**発射角度(1次元の回転)のみ**とした。マウス/タッチは角度を直接指定する形で2次元入力を受け付けるが、内部的には常に「固定ピボットからの角度」1つに変換される点で、既存5作の自由な2次元操作とは質的に異なる、据え置き型ターレットの操作感にした。
4. **世界観・配色・題材を変更**: 宇宙のネオン射的場(シアン/マゼンタ)、データトンネルのサイバー空間(緑基調)、夜の灯台の海洋モチーフ(濃紺/琥珀金)、坑道の結晶鉱脈(黒紫/マゼンタ)、暗い森の樹冠(焦げ茶/オレンジ)のいずれでもなく、氷に閉ざされた洞窟の見張り砲台という寒冷モチーフとし、配色は深い藍黒(#030b12 系)と氷のシアン白(#8fe9ff / #eafeff 系)を基調にした。対象も光のオーブ、パケット、信号灯、結晶、エンバーではなく、洞窟内を漂う無機質な蒸気の光点(ウィスプ)にした。実在の人物・組織・ロゴ・キャラクターは一切参照していない。

## 主な設計判断

1. **固定ピボット + 角度のみの照準モデル**: 発射位置 `launchX()/launchY()` は常に画面下中央に固定し、`aimAngle` という単一のラジアン値のみを状態として持つ。マウス/タッチは `Math.atan2` で角度に変換して直接セットし、キーボードは `AIM_ROT_SPEED` による角速度でインクリメンタルに回転させる。角度は `AIM_LIMIT`(約77度)でクランプし、常に洞窟の奥(上方向)へ向けて発射されるようにした。
2. **飛翔物としての銛のシミュレーション**: 銛は `{x, y, dx, dy, bornAt, chainCount, hitSet}` を持つオブジェクトとして `harpoons` 配列で管理し、毎フレーム位置を更新しながら未ヒットのウィスプとの距離判定を行う。同一銛が同じウィスプに二重ヒットしないよう `hitSet` で既ヒット対象を記録し、貫通のたびに `chainCount` を加算する。銛は最大飛翔時間(`HARPOON_MAX_LIFE`)超過または画面外離脱で消滅し、その時点の `chainCount` に応じて HIT/CHAIN/MISS を確定させる(0 なら MISS でコンボリセット、1 以上なら得点+コンボ継続、2 以上なら追加で CHAIN ボーナス)。
3. **貫通ボーナスのスコア式**: 1 体ヒットで `BASE_POINTS(10) × multiplier`、2 体目以降は 1 体ごとに `CHAIN_BONUS(6) × multiplier` を加算する。EMBER CANOPY の「乗算コンボ」や SIGNAL PURGE の「5コンボごとに倍率上昇」とは別に、本作は「1発の質(貫通数)」と「連続成功の量(コンボ倍率)」を掛け合わせる二軸のスコアリングにした。
4. **リロードによる連射制限**: 発射後 `RELOAD_TIME(0.22秒)` は次弾を撃てない。連打で軌道を試行錯誤する戦法を防ぎつつ、EMBER CANOPY のスイング再チャージ(0.42秒)より短く設定し、投射物ゲーム性(飛翔時間そのものが間合いになる)に対して過度な制約にならないようにした。
5. **検証は「本物の実行」で行う**: `smoke.mjs` は Node 標準の `vm` 上でインラインスクリプトを実際に実行し、⑥は `finish()` を直接呼ばずに約63秒分のフレームを進めて自然にタイムアップさせ、その後 REPLAY ボタンのリスナーを発火してスコア0・残り60秒への初期化と再進行を確認する。ゲーム側は UI と同じ関数を束ねた `window.__GAME__` フック(`state`/`score`/`timeLeft`/`start` を含む)を getter で公開し、検証専用の別ロジックは持たない。なお、銛の貫通判定など実際のゲームプレイ挙動自体は smoke.mjs の検証対象ではなく、実装の妥当性はコードレビューで担保している。
6. **誤タップガード**: CAVE SECURED の瞬間に連打していると即 REPLAY されてしまうため、リザルト表示から 0.6 秒(smoke.mjs が要求する 1 秒以下の範囲内)は再開入力を無視する。
7. **要素取得・時間管理・環境依存の方針**: 要素取得は `document.getElementById` のみを使用(`querySelector` 系は不使用)。時間は `performance.now()` を経由する `requestAnimationFrame` のタイムスタンプのみで管理し、`Date.now()`/`setInterval`/`setTimeout` には依存しない。`AudioContext` は存在チェック+`try/catch` で包み、無い環境でも例外なく完走する。`localStorage`/`matchMedia` は一切使用していない(ベストスコアはセッション内メモリのみ)。
8. **UI言語とフォント**: CONSTRAINTS.md の英語UI制約に従い、タイトル・操作説明・ボタン・HUD・リザルト表示などプレイヤー向けテキストはすべて英語のみとした(本 devlog は対象外のため日本語で記録)。`font-family` は `sans-serif` と `monospace`(数値表示のみ)の generic family に限定し、`system-ui` を含む固有フォント名・フォントブランド・外部フォントは一切使用していない。
9. **題材の安全性**: 対象は無機質な光の粒(ベイパーウィスプ)であり、人・生物・実在の名称・ロゴ・歌詞は一切使用していない。血液等の表現なし。金融・法律・医療・政治の要素なし。暴力性を想起させる表現もない(「洞窟の見張り砲台が漂う蒸気を捕捉する」という穏やかな観測・保全のメタファーに終始し、対象を「破壊」ではなく「捕捉」として扱っている)。

## 未解決事項

- スモークはロジックの実行検証であり、実ブラウザでの描画品質・入力遅延・タッチ操作の触感、および貫通ヒットの実プレイでのバランス(軌道が重なる頻度など)は自動検証していない(依存ゼロを優先し、Playwright 等の追加は見送った)。
- iOS Safari 実機でアドレスバー分の `innerHeight` 変動が起きた場合、回転直後の 1 フレームだけ古いキャンバスサイズで描画される可能性がある(`resize` イベントで追従はするが、リサイズ完了までの過渡的なズレは残る)。
- ウィスプの出現間隔・速度範囲・砲台の可動角度(±77度)・リロード時間(0.22秒)は固定値であり、プレイヤーの実力に応じた動的な難易度調整は行っていない。
- ベストスコアはセッション内メモリのみで、タブを閉じると消える(永続化には `localStorage` が使えるが、`file://` 直開き環境での例外リスクを避け今回は見送った)。
- 貫通ヒットの当たり判定は銛の現在位置とウィスプ中心の距離のみで行っており、非常に高速なフレームレート低下(dt が大きい環境)では銛がウィスプをすり抜ける(トンネリングする)可能性がある(`dt` は 0.1 秒でクランプしているが、極端な低フレームレート環境は未検証)。
