# devlog — seed-014

## 作品名
SPIRE DRIFT

## テーマ選定理由(既存作品との差別化)
既存 works/seed-001〜013 は、照準・リング・ロック対象・ヒートノードなど「毎回リセットされる的」に対してタップ/ホールド/ドラッグで反応するものが大半で、ある1回の決定が生む結果は基本的にその場のスコアだけに反映され、次の的の難度そのものを変えることはなかった(唯一 CORE OVERLOAD は複数対象の並行管理だが、対象自体の性質は決定に応じて変化しない)。SPIRE DRIFT のコアメカニクスは、タップで積み木を落とすたびに「重なった幅だけが次の土台の幅になる」ことで、プレイヤー自身の精度がそのまま次の一手の難度(土台の狭さ・ブロックの揺れ速度)を決定づける点にある。これはフェーズ3の C7(慣れた頃に新戦略が要求されるか)で最終候補3つ(MARQUEE HAUL: 毎ラウンド独立したリスク/リターンの箱選択、PATTERN BREAK: 毎ラウンド独立した記憶の再現)より明確に強く、かつ C1(既存作との違い)でも「積み上げが状態として残り、後続の判断空間を物理的に狭める」構造は他のどの作品にも存在しないため、これを選定した。

## 主な設計判断
- タワーは配列 `towerBlocks` として保持し、各層は `{x, halfW}` のみを持つ。新しい層は「現在の層」と「落下中ブロック」の区間の重なり(overlap)そのものを幅として確定させる(`drop()`)。これにより、はみ出した部分を描画上カットする演出を別途作る必要がなく、状態そのものが必然的に狭くなる。
- 画面には常に「現在の最上層」が固定 Y 座標(`TOP_Y`)に描画され、下の層は `layerScreenY()` でインデックス差 × `LAYER_H` だけ下にずれて描画される。タワーが高くなるほど古い層は画面外(下)へ流れて消えるだけなので、ページスクロールなしで際限なく積み上げられる(CONSTRAINTS の「1画面で完結」を canvas 内カメラで満たす)。
- ミス(重なりが `MIN_OVERLAP` 未満)はゲームオーバーにはせず、コンボを 0 に戻して同じ幅のまま次のブロックを再スポーンさせる。60秒間の連続プレイを前提とする本リポジトリの FPS 風トイの性質上、1回のミスで詰む古典的な「積み上げゲーム」の失敗デザインは採用しなかった。
- ブロックの左右往復速度は `BASE_SPEED + towerBlocks.length * SPEED_PER_LAYER + elapsed * SPEED_PER_SEC` で、積み上げた段数と経過時間の両方から上がる。序盤に覚えた「ゆっくり狙う」感覚が終盤では通用せず、狭い足場をより速い揺れの中でタップする必要が出てくる(C7)。
- 検証用フック `checkSuccess()` は、ハンドラが立てるだけの真偽フラグではなく `towerBlocks.length > 1` という実際に描画されているタワー配列の長さを直接読む形にした。初期土台の半幅(130px)と最初のブロックの往復範囲(画面中央から左右320pxまで)の関係上、`MIN_OVERLAP`(28px)未満になる完全ミスの領域は往復レンジの一部に限られるため、`primary_input=tap` の最初の数回のタップでほぼ確実に1回はロックが成立し、`scripts/interaction-smoke.mjs` の実ポインタ駆動でも安定して成功する設計にしてある。
- キーボード操作は Space/Enter に統一し、タイトルでは開始、プレイ中はタップと同じ `drop()`、リザルト画面ではリプレイに割り当てた(マウスを使わない PC 操作経路の確保)。

## 未解決事項
- `SPEED_PER_LAYER` / `SPEED_PER_SEC` / `MAX_SPEED` の数値は、序盤は寛容で終盤はタイトになるよう机上で決めた初期値であり、実プレイでの体感難度カーブ(特に終盤 520px/s が速すぎないか)は未検証。
- スコア式(`30 + precision*50` に加えパーフェクト時のコンボボーナス `combo*10`)は、コンボを維持する戦略と毎回丁寧に狭い的を刻む戦略の得点期待値がどの程度拮抗するかを実測せずに設定しており、片方が支配的になっていないかは要検証。
