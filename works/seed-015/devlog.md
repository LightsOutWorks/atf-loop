# devlog — seed-015

## 作品名
CARGO TILT

## テーマ選定理由(既存作品との差別化)
既存 works/seed-001〜014 の大半は、単一の的(リング・ノード・タワーなど)に対してタップ/ホールド/ドラッグで反応し、1回の決定が生む結果はその場のスコアかせいぜい直近の難度上昇にしか波及しない(例外は SPIRE DRIFT のタワー幅の連鎖、CORE OVERLOAD の並行ノード管理)。CARGO TILT のコアメカニクスは、落下する荷物を左右どちらのドックに送るかという1回のタップが、シーソーの傾き(左右のドック積載量の差)という「常に画面に表示され続ける物理状態」を直接動かし、その傾きが次のタップの安全マージンをそのまま決めるという点にある。フェーズ3の最終候補3つ(MASS SWAP: 2タップでの並び替え、QUEUE CUT: 単一レーンのゲート開閉)と比較して、C6(即座のフィードバック)では傾きアニメーション・積載バー・スコアポップアップが1タップごとに同時に返る点で最も強く、C3(決定の独自性)でも「毎回の決定が継続的な物理状態を通じて次の決定の安全域を狭め続ける」構造が他候補より明確だったため、これを選定した。

## 主な設計判断
- ドック積載量は `docks.left.load` / `docks.right.load` の2値のみで保持し、傾き `tilt` は毎タップ後に `(right.load - left.load) / TILT_SCALE` から同期的に再計算する。描画用の `visualTilt` は別変数にして毎フレーム `tilt` へ線形補間するだけにし、ゲームロジックの状態(`tilt` そのもの)とアニメーションを分離した。
- `|tilt| >= 1` になった瞬間を「こぼれ」と定義し、重い側のドックの積載量を即座に 0 に戻し、スコアを軽く減点する。ここでゲームオーバーにはせず、60秒間の連続プレイを前提とする本リポジトリの FPS 風トイの性質上、1回の失敗で詰む設計は避けた(SPIRE DRIFT の「ミスはコンボ0でリスポーンのみ」という判断を踏襲)。
- 各ドックは `SHIP_LIMIT` に達すると自動で出荷され、積載量が超過分を残して減り、まとまったボーナス得点が入る。荷物の重さ `rollWeight()` は経過時間に応じて取りうる最大値が 1→2→3→4 と伸びるようにし、序盤に覚えた「軽い荷物を適当に振り分ける」感覚が終盤には通用せず、重い荷物をどちらに送るかの判断がより重要になる(C7)。
- 入力は `canvas` 全体を左半分/右半分の2ゾーンとして扱う(`clientX` が矩形幅の中央未満かどうかだけで判定)。ドックやシーソーの描画位置に関わらず、画面上のどの座標をタップしても必ずどちらかのドックへの有効な入力になるため、`scripts/interaction-smoke.mjs` の固定グリッド座標によるブラインドタップでも初回のタップから確実に `checkSuccess()`(`cratesPlaced >= 1`)が成立する。
- 検証用フック `checkSuccess()` は、入力ハンドラが立てるだけの真偽フラグではなく、実際に `assign()` 内でインクリメントされる `cratesPlaced`(画面下部の SCORE 表示にも連動する実データ)を直接読む形にした。PC 操作用に ArrowLeft/ArrowRight(および a/d)を左右ドックへの割り当てに、Space/Enter を開始・リプレイに割り当てている。

## 未解決事項
- `TILT_SCALE`(16)・`SHIP_LIMIT`(10)・`SPILL_PENALTY`(15)・`SHIP_BONUS`(50)の数値は、序盤は寛容で終盤にかけて荷物の重さが上がることで自然にシビアになるよう机上で決めた初期値であり、実プレイでの体感難度カーブ(特に終盤の「毎回ギリギリ」感が強すぎないか)は未検証。
- 「こぼれ」時に重い側の積載量を全損させる設計と、出荷時に超過分だけ残す設計の非対称性が、プレイヤーに意図通り「なるべく出荷させたいが溢れさせたくない」という緊張感を生んでいるかは実測していない。
