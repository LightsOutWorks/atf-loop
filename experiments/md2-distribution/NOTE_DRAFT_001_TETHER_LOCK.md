## タイトル案

**全チェックPASSのゲームが、マウスでもタッチでも一度も遊べなかった——AI自動生成パイプラインの検証設計に空いていた穴の実録**

（サブ候補: 「自動テスト6/6 PASS、内容審査PASS、それでもスコア0しか出ないゲームが公開された話」）

## 本文

**TL;DR**

- AIにブラウザゲームを作らせて自動公開する仕組みを運用していたら、構造テスト全PASS・内容ゲートPASSのゲームが「マウスでもタッチでも一度もプレイ開始できない」状態で公開されていた
- 原因はコード1箇所ではなく検証設計の盲点。「宣伝した操作が、宣伝した結果を生むか」を、どの検証も見ていなかった
- ゲームは直さず検証を増やした。壊れた実物は証拠としてそのまま公開してある

---

2026年8月2日。運用していた無人生成パイプライン（生成→自動テスト→内容審査→公開）が出したゲームの一つ「TETHER LOCK」を自分で遊んでみて、何度やってもスコアが0のまま終わることに気づいた。

終了画面の実測値はこうだった。

```
SIGNAL LOST / 0 pt / LOCKED 0 / LOST 66 / RELEASED 0
```

ドリフター（ゲーム内の捕獲対象）は66体流れている。つまりゲームの進行自体は動いている。捕獲（LOCKED）と解放（RELEASED）だけが両方ゼロ。

最初は「自分が下手なだけ」「操作を理解していないだけ」と処理しかけた。ここが一番危なかったところで、**プレイヤー自身が「自分の習熟不足」と誤分類すると、バグは永久に発見されない**。

### 原因は単純で、しかしテストでは見えない場所にあった

コードを調べると、ホールド状態を開始する関数 `beginHold()` の呼び出し箇所は2つしかなく、両方とも通常操作からは到達できなかった。

1. 1つ目は `if (!holding) { ...; return; }` の内側にあり、「既にホールド中」でないと実行されない。つまり進行中のホールドの対象変更はできるが、**開始だけができない**
2. 2つ目は物理キーボードの Space / Enter からのみ呼ばれる

結果、ポインタ入力（マウス・タッチ共通）では一度もロックを開始できず、物理キーボードだけが動く。キャンセル処理も `if (!holding) return` で無音の空振りになるため、RELEASEDも0のまま。LOSTだけが増えるのは、期限切れ判定が入力と独立に走っているから。

タッチ固有の問題でもiOS固有の問題でもない。イベント処理の設定はすべて正常だった。**「到達できない正常なコード」**だった。

### なぜ全部の検証をすり抜けたか

| 検証 | 見ていたもの | 結果 |
|---|---|---|
| 自動スモークテスト（6項目） | ファイル存在・構文・読み込み・状態遷移の構造 | 6/6 PASS |
| 内容ゲート | 表現・題材の適切性 | PASS |
| （存在しなかった検証） | **宣伝した操作が、宣伝した結果を生むか** | — |

構造テストは「動くか」を見る。内容審査は「出してよいか」を見る。だが「マウスで遊べると書いてあるゲームが、マウスで遊べるか」は、誰も見ていなかった。

これがこの記事の一番の主張だ：**自動検証の網は「作った人が検証しようと思った軸」しか覆わない。事故は軸そのものの欠落から来る。**

### その後どうしたか

ゲームは直していない。意図的に壊れたまま公開してある。理由は2つ。

1. 修正すると「検証の穴が実害を出した実物」という一次証拠が消える
2. 直すべきはゲームではなく検証設計だった

やったのは検証側の追加で、「主要操作が宣言どおりの最小の状態変化を起こすか」を機械で確認する層を足した。以後の生成物はこの層を通る。

### 読者向けQ&A

**Q. 自分のCI/自動テストで同型の穴を見つけるには？**
A. 「このプロダクトの宣伝文に書いてある操作を、テストは実際に実行しているか」を宣伝文側から逆引きする。テストコード側から見ると網羅している気になるが、ユーザー向けの説明文から見ると大穴が見つかることがある。

**Q. AI生成コード特有の問題？**
A. 発生源としてはAIに限らない。ただしAI生成×自動公開は「人間が一度も触らないまま世に出る」経路を作るので、この型の事故の到達率が構造的に上がる。

**Q. スコア0に他の原因もあり得たのでは？**
A. あり得た。習熟不足・難易度・UI・バグは症状（スコア0）だけでは区別できない。だから観測は症状ではなく原因で分類する、が運用ルールになった。
