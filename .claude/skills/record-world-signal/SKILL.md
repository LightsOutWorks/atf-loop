# record-world-signal

HumanのWorld Signal報告を、該当台帳へ正しい等級・欠落なしで転記し、次の一手を1案起草して止まるスキル。**Humanから報告が渡された時だけ起動するオンデマンド処理**であり、観測の自動化ではない（X Reply Ingestionの自動観測はD-003でHOLD。本スキルはその領域に踏み込まない）。

## 位置づけ

- **入力はHuman報告のみ**: スクリーンショットの内容・文章・口頭メモ。
- **本スキルがX・SNSを読みに行かないのは、能力の欠如ではなく決定と停止線による。** X Reply Ingestionの自動観測はD-003（Current Operational Priorityの分離）で `HOLD` / budget `UNAPPROVED` であり、読取・監視・API取得は下の停止線が禁じている。**「harnessからXを読めない」を永久的な能力制約として書かない**——到達性は環境ごとに変わる観測値であって規則ではない。仮に読める環境であっても、D-003が解除されるまで読みに行かない。
- **正本を複製しない**: 記録規律・凡例・Stage定義・文面規律の正本は各台帳と契約が持つ。実行のたびに該当台帳の規律を読む。本ファイルと正本が矛盾したら**常に正本が勝ち**、矛盾自体を欠陥として報告する。
- 記録の重さは対象の規律に従う。**このリポジトリはPUBLICである**——PII規律は転記前に必ず適用する。報告として渡されたスクリーンショット・画像・音声・生データそのものはrepoへ入れない（§4）。

## 手順

### 1. 対象の特定

`experiments/INDEX.md` から、報告が帰属する実験と台帳を特定する（返信・接触反応 → 接触系台帳（例: `experiments/batch-1/LEDGER.md`）/ プレイ・納品観測 → `experiments/desire-to-game/LEDGER.md`）。

**探索はACTIVEを優先するが、ACTIVEに限定しない。** `HOLD` / `HISTORICAL` / `NO-GO` / `RETIRED` の実験へ遅延返信や事後Signalが返ることは実際に起こるため、候補から除外しない（例: E-013は `HISTORICAL — result: VOID` だが、Day 1に送信済みの4件へ今後返信が返りうる）。**status上の終了は、その実験へSignalが返らないことを意味しない。**

帰属は **join key**（contact id・participant id・元投稿URL・送信文面・ファイルSHA-256等）と報告内容の照合で決める。**join keyと報告内容で一意に特定できない場合はHumanに確認する。推測で割り当てない。** join key自体が報告から取れない場合も同じ——聞くか `UNKNOWN` と書く。ACTIVEに1件、終了済みに1件の候補が並ぶ場合も、「ACTIVEだから」を決め手にしない（それはjoin keyではない）。

**E-014の台帳は記録面が3つに分かれる。混同しない**（正本 = `experiments/desire-to-game/LEDGER.md`）: ①**判定母集団**（Desire → 納品記録 / Signal記録 / Repair Request Log）②**Retrospective Seed Corpus**（承認前・承認前後が未確認の既存ゲーム。判定母集団の外）③**Evolution Transfer Log**（前作の学びの次作への移転）。eligibilityの既定は `UNKNOWN` であり、**推測で `ELIGIBLE` にして判定母集団へ入れない。**

終了済み実験へ事後Signalを転記しても、**その実験の確定verdictは書き換えない**（`VOID` を `FAIL` として学習しない等）。追記は事後Signalとして日付付きで行い、確定判定の見直しが要ると判断した場合はその旨を指摘するだけに留め、再判定はHuman裁定に委ねる。

### 2. 対象台帳の規律を読む

特定した台帳の運用規則・記録規律・凡例と、直近の関連記録（Reply Log・事前登録済みの判定条件）、必要なら当該実験の契約を読む。記録の列・分類・Stage語彙はすべて台帳側の定義に従う。

### 3. 等級付けと分離

- **FACT**: Human報告に含まれるverbatim・スクショ記載値・Humanが確認したと明言した事実。出典（報告日時・確認手段）を付けて記録する。**台帳へ書く形は §4 のverbatim / PII規律に従う**（等級がFACTであることと、原文をそのまま公開repoへ置いてよいことは別）。
- **INFERENCE**: 解釈・分類・推定。必ずFACTと区別してラベルする。
- **UNKNOWN**: 報告に含まれない値。**補完しない。それらしい値・時刻・数値を発明しない。** 精度も落とさない——「昨日の夜」しか報告が無ければ、分単位の時刻を作らず日付レベル＋精度UNKNOWNで書く。
- 台帳が定める分離を適用する: **Expressed / Observed**（発言と行動の矛盾はObserved優先）、**Repair / Continuation**（E-014: Repair Requestは「次のDesire」にカウントせずRepair Request Logへ）、その他対象台帳固有の分離。

### 3-a. E-014系報告の分離（Retrospective Seed Corpus / Evolution Transfer Log）

E-014またはRetrospective Seed Corpusのゲームに関する報告では、次の4つを**それぞれ別の記録として**扱う。1つの行に混ぜない。

| 報告の中身 | 何として記録するか |
|---|---|
| 作った・渡した（制作・納品） | Factory側の事実。**World Signalではない** |
| ヒロの評価（「出来が良かった」等） | **Human Taste Signal**。World SignalでもE-014のPASS証拠でもない |
| 参加者本人の行動・発話（遊んだ・また遊びたい・人に見せた・直して） | **World Signal**。さらにRepair / Continuationを分ける（§3の分離規律） |
| 前作の学びを次作へ使った / 使った結果 | **Evolution Transfer Log** の移転実績・適用後Signal |

- **帰属**: `game_id` / `participant_id` / artifactのファイル名・SHA-256のいずれでも一意に特定できない場合は `UNKNOWN` と書く。推測で割り当てない（§1と同じ規律）。
- **artifact**: ゲーム本体・Claude Artifact URL・画像・動画・音声はrepoへ入れない（§4「生データ自体をcommitしない」と同じ）。台帳へ入るのは**ファイル名とSHA-256だけ**であり、**SHA-256が取れなければ `UNKNOWN`。架空のハッシュを作らない。**
- **参加者**: 匿名ID（P1〜）と続柄カテゴリのみ。**1人へ複数本作られていても参加者Nは1**（ゲーム件数と参加者数を混同しない）。
- **学びの等級**: `source_game_id` の無い一般論は登録しない。**抽出しただけでは「Factoryが進化した」と書かない**——後続ゲームへ適用された時点で**移転実績**、適用後のHuman TasteまたはWorld Signalが取れた時点で `支持` / `反証` を記録する。**取れていない間は効果を `UNKNOWN` のまま残す。** 悪化した学びも削除せず `反証` として残す。

### 4. 転記（最小差分・追記のみ）

該当台帳へ最小差分で追記する。既存行・過去の記録は書き換えない（訂正は日付付き訂正追記）。日時・対象・join key・証拠等級を欠落させない（欠落する場合は `UNKNOWN` を明記して欠落自体を記録する）。

#### verbatimとPII——優先順位は一意

このリポジトリはPUBLICであり、**PII除去が常に先に効く**。したがって「原文のまま保存」はしない。公開repoへ保存してよいverbatimは、**PIIを除去・匿名化したうえで、発言の意味・語調・強度を変えていないverbatim**だけである。

- **除去箇所は伏字マーカーで明示する。** 黙って削らない——削除の痕跡が消えると、原文がそう書かれていたのか編集されたのかが後から区別できなくなる。
- 種別が分かる形で置換する: `[REDACTED:実名]` / `[REDACTED:社名]` / `[REDACTED:URL]` / `[REDACTED:連絡先]`。人物は匿名ID（E-014はP1〜）と続柄カテゴリで表す。
- **PII以外を書き換えたなら、それはもうverbatimではない。** 要約・言い換え・敬体常体の変換・語尾の整形を行った時点で等級をINFERENCEへ落とし、verbatimとして記録しない。
- **PIIを除くと意味が保てない発言は、verbatimを載せない。** INFERENCEの要約だけを残し、原文は台帳へ入れない。
- 実名・顔・年齢・家族構成・勤務先・住所・連絡先の特定につながる記述は、verbatim内かどうかを問わず書かない。

#### 生データ自体をcommitしない

報告として渡された**スクリーンショット・画像・音声・動画・メール原文・DMのエクスポート等の生データは、public repoへ追加しない**（`experiments/` 配下への添付・貼付・base64埋め込み・別ディレクトリへの退避を含む）。台帳へ入るのは上記規律を通したテキストだけであり、原本の所在はHuman側に留める（台帳には「原本: Human保持・repo外」と書く）。

#### 判定窓の起点

**起点は、各契約に事前登録された起点事象を使う。「常に送信時刻」で書かない**——起点は実験ごとに異なる。

1. 当該実験の契約・台帳の事前登録済み判定条件を読み、**その窓の起点事象が何と定義されているか**を確認する（例: Human送信時刻 / 納品時刻 / 初回プレイ時刻 / 投稿時刻 / Repair納品時刻）。
2. その起点事象の**実測時刻**で窓を計算する。
3. **返信timeoutのように、起点事象がHumanの送信そのものである窓に限り、実際の送信時刻を使う。** 受信時刻・起草時刻・commit時刻で代用しない（Batch 1 Reply Log 004の実測欠陥）。送信はHuman Gateであるため、起草から送信までの間隔は `UNKNOWN` であり、起草時刻を送信時刻とみなさない。
4. 起点事象が契約に事前登録されていない、または起点事象の実測時刻が報告から取れない場合は、**窓を自分で定義しない。** 起点 `UNKNOWN` として記録し、Humanに確認する。
5. 事前登録済みの判定条件は結果を見てから動かさない（`CONSTRAINTS.md` Part I §6）。

### 5. 整合検査（必要な場合のみ）

記録した事実が `CURRENT_STATE.md` の現在値（累積REPLY数等）や `experiments/INDEX.md` のstatus行と食い違う場合のみ、その箇所を指摘し、日付付き訂正追記を**提案**する。関係のない整合監査へ広げない。

### 6. 次の一手の起草（1案のみ）

台帳の規律・事前登録済みの判定条件・分類結果から、次の一手を**1案だけ**起草する（HI-11: 選択肢を並べて返さない）。返信文の既定は**40〜120字・質問1つ・オファーなし・リンクなし・自己紹介なし・毎回個別文面**（詳細な文面規律・撤退シグナルは対象台帳と `direction/SALES_OS_2026-08.md` が正本）。事前登録済みの分岐（「〜が返ったら閉じる」等)がある場合はそれに従い、**上書きしない**。

会話の往復をファネルの前進と読み替えない。Stageの変更は台帳の定義が根拠づける場合だけ差分として提案し、確定はHuman確認に委ねる。

**E-014系の場合**: 次の一手として**新しいゲーム制作を自動提案しない**——既存のRetrospective Seed Corpus（未分解の既存ゲーム）の回収を先に置く。不足情報は**ゲームごとに何度も聞かない。全作品分を一度に返せる最小バッチ表1枚へ圧縮し、Humanへ1回だけ依頼する**（HI-2: 1ターンにつきHuman Actionは原則1つ）。

### 7. 停止

起草を提示して止まる。**送信しない。**

## 停止線（常に適用）

行わないこと: 第三者への送信・投稿・DM（`CONSTRAINTS.md` Part I §4 Human Gate）/ X・SNSの読取・監視・ポーリング・API取得（D-003により `HOLD`。**環境上読めるかどうかとは無関係に行わない**）/ 常駐処理・スケジュール登録・通知の設定 / **報告として渡された生データ（スクリーンショット・画像・音声・動画・原文エクスポート）のpublic repoへのcommit**（E-014系ではゲーム本体HTML・Claude Artifact URLも同じ扱い） / 確定済みverdictの書き換え / **E-014の契約・PASS / FAIL / VOID条件・判定点の変更**（Retrospective Seed Corpusへの記録でFunnel現在値・判定点・Verdictを動かさない） / mainへのmerge / 支出。記録の反映はbranch上のcommitまでとし、PR作成は依頼の文脈に従う。mergeは常にHuman Gate。
