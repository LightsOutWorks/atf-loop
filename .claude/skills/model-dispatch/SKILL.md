# model-dispatch

実作業を適切なモデルへ委譲するための振り分け方針。目的は2つ——**軽い作業に高価なモデルを使わない**こと、**重い判断を軽いモデルに任せない**こと。

## 本体モデルとサブエージェントの関係（2026-08-14 Human裁定）

**本体（セッション）とサブエージェントは別の層である。** 混同すると「振り分けたつもり」で何も起きない。

- **本体モデルの自動切替は `.claude/settings.json` の `"model": "opusplan"` が行う。切替は Plan中のOpus／実装中のSonnet の2値**である。これ以上の粒度は本体側には無い。
- **Fable / Sonnet / Haiku の細かな振り分けは、本体の切替ではなくサブエージェントへの委譲で行う。** 本設定を入れても本体がFableやHaikuになることはない。下の振り分け表が扱うのは委譲先の層だけである。
- **`/model` による任意切替はHuman操作**であり、Claudeが勝手に行う領域ではない。Humanが `/model` で選んだ場合はそれが優先する。
- **project設定は新規sessionの初期値である。** resumeした既存sessionは保存時のモデルを維持し、この設定では変わらない。「settings.jsonを変えたのに挙動が変わらない」はresumeでは正常な結果であって欠陥ではない。

### hookが行うこと・行わないこと

`.claude/settings.json` の UserPromptSubmit hook は、**毎ターン本方針を再注入するだけ**である。

- **hookはSkill呼出しを確定発火させない。** 「hookでSkillが確定発火する」という説明は誤りであり、撤回する。hookが保証するのは方針テキストが毎ターン文脈に入ることだけで、Skillが実際に呼ばれるか・振り分けが実行されるかは保証しない。
- したがって**発火率は実測対象**である。注入されていることをもって「毎回振り分けられている」と書かない。

## 振り分け表

| 依頼の型 | 委譲先 | 理由 |
|---|---|---|
| ファイル横断の検索・列挙・大量読みと要約・形式変換・定型転記の下準備・単純スクリプト実行 | **quick-worker**（haiku） | 判断が少なく、速さと安さが正義。生データを本体のコンテキストへ流し込まずに済む |
| 通常のコード実装・文書ドラフト・単一文書の分析・テスト作成と実行 | **standard-worker**（sonnet） | 標準的な品質判断で足りる |
| 敵対的検証・実験契約や判定基準の設計レビュー・正本間の矛盾分析・難バグ診断・戦略分析・最終レビュー | **deep-worker**（fable） | 深さが結果を左右する。ここをケチると事後修正コストの方が高くつく（E-013の実測） |
| 追記のみ台帳への記録で、signal分類・事前登録条件との突合・正本間整合を伴うもの | **判定は deep-worker**、書き込みは本体または standard-worker | 「記録」に見えて実体は判定。転記と判定を分けないと、判定を軽いモデルへ落とすことになる |

## 振り分けない（本体がそのまま行う）

- **会話・即答・短い質問への回答** — 委譲のオーバーヘッド（コンテキストの再構築）の方が高くつく
- **ユーザーへの確認・Human Gateに関する判断** — 委譲対象は作業であって判断ではない
- **会話の文脈全体が本質で、切り出して渡せない作業**
- **数分で終わり、かつ出力が小さい作業** — 委譲の往復より自分でやる方が速い。ただし**時間が短くても生出力が大きい作業（横断grep・全文スキャン・大量ファイル読み）は委譲する**。本体のコンテキストへ生データが流れ込む損失の方が、往復コストより高い

## 運用規則

1. **迷ったら1段上に振る。** quick か standard で迷えば standard、standard か deep で迷えば deep。安全側の誤りは金の無駄で済むが、逆は品質事故になる。
2. **並列委譲は、時間短縮になる場合だけ。** 条件は2つとも満たすこと——(a) 作業が互いに独立している（一方の結果が他方の入力にならない）、(b) 委譲の往復・同じファイルの重複読解・戻ってきた結果の突合を**含めても**、直列や本体単独より速い。**並列数を増やすこと自体を目的にしない。** 対象が単一文書・単一検索なら検討不要（並列にしない理由をわざわざ書かない）。依存がある作業を無理に並列化すると、同じ正本を各エージェントが読み直す分だけ遅く・高くなる。
3. **ユーザーのコスト・品質指定は表より優先する。**「安く」「軽く」→ 1段下げる。「しっかり」「徹底的に」「深く」→ deep-worker、必要ならWorkflowで検証段を付ける。**下限は quick-worker まで**（ただし対象ファイルが特定済みで、本体のコマンド1回で終わり、**かつ出力が小さい**なら委譲しない。それが最安。出力が大きければ「安く」と言われていても委譲する——上の生出力の但し書きが優先する）。**上限は deep-worker**。
4. **既存スキルが該当する作業はスキルが勝つ。** モデル階層へ振る前に、**実在するスキルを確認**し、該当するものがあればそれを使う（内部の重い工程を deep-worker に載せるのは可）。**スキル名を記憶で呼ばない**——スキルは増減する。該当しそうなスキルが実在しなければ、黙って振り分け表へフォールバックしてよい。**欠陥としてHumanへ報告するのは、正本や既存文書がそのスキルの存在を前提に言及しているのに実在しない場合だけ**（`CLAUDE.md` §2）。単に該当スキルが無いだけなら報告不要——毎回「欠陥ではない」と書かない。
5. **成果物の検証は起草より1段上で。** standard-worker が作った重要成果物の最終確認は本体か deep-worker が行う。**既定は本体**——成果物が小さく、判断に要る正本文脈を本体が既に持っているなら本体で足りる。deep-worker を使うのは、本体の文脈の外にある判断（複数正本の突合・敵対的検証）が要るときに限る。「重要だから念のため deep」は 1段分の無駄になる。
6. **委譲プロンプトには、その作業に必要な最小限の文脈・制約・実在確認済みパスだけ渡す。** サブエージェントは会話を見ていないので省略はできないが、**会話全体を詰め込むのは別の失敗**である。渡すのは3種類に限る——(a) その作業の達成に必要な前提、(b) 破ってはいけない制約と期待する出力形式、(c) **実在を確認したファイルパス**（記憶や推測で書かない。存在しないパスは探索コストと誤読を生む）。関係のない経緯・他タスクの結論・正本の全文引用は渡さない（読解コストを増やし、無関係な制約に引きずられた出力を生む）。エージェントが自分で読める内容は、貼らずにパスで渡す。ユーザー向けの日本語文面は戻ってきた生データから本体が仕上げる。

## ユーザーへの見せ方

どこへ振ったかを冒頭で一言だけ伝える（例:「検索はquick-worker、検証はdeep-workerに投げます」）。振り分けの講釈はしない。
