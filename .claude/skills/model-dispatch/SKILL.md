# model-dispatch

実作業を適切なモデルへ委譲するための振り分け方針。目的は2つ——**軽い作業に高価なモデルを使わない**こと、**重い判断を軽いモデルに任せない**こと。

## 振り分け表

| 依頼の型 | 委譲先 | 理由 |
|---|---|---|
| ファイル横断の検索・列挙・大量読みと要約・形式変換・定型転記の下準備・単純スクリプト実行 | **quick-worker**（haiku） | 判断が少なく、速さと安さが正義。生データを本体のコンテキストへ流し込まずに済む |
| 通常のコード実装・文書ドラフト・単一文書の分析・テスト作成と実行 | **standard-worker**（sonnet） | 標準的な品質判断で足りる |
| 敵対的検証・実験契約や判定基準の設計レビュー・正本間の矛盾分析・難バグ診断・戦略分析・最終レビュー | **deep-worker**（fable） | 深さが結果を左右する。ここをケチると事後修正コストの方が高くつく（E-013の実測） |
| 追記のみ台帳への記録で、signal分類・事前登録条件との突合・正本間整合を伴うもの | **判定は deep-worker**、書き込みは本体または standard-worker | 「記録」に見えて実体は判定。転記と判定を分けないと、判定を軽いモデルへ落とすことになる |

## 振り分けない（本体がそのまま行う）

- **会話・即答・短い質問への回答** — 委譲のオーバーヘッド（コンテキストの再構築）の方が高くつく
- **ユーザーへの確認・Human Gateに関する判断** — 委譲対象は作業であって判断ではない
- **会話の文脈全体が本質で、切り出して渡せない作業**
- **数分で終わり、かつ出力が小さい作業** — 委譲の往復より自分でやる方が速い。ただし**時間が短くても生出力が大きい作業（横断grep・全文スキャン・大量ファイル読み）は委譲する**。本体のコンテキストへ生データが流れ込む損失の方が、往復コストより高い

## 運用規則

1. **迷ったら1段上に振る。** quick か standard で迷えば standard、standard か deep で迷えば deep。安全側の誤りは金の無駄で済むが、逆は品質事故になる。
2. **並列に振れるものは並列に振る。** 独立した作業は同一ターンで複数エージェントを起動する。対象が単一文書・単一検索なら検討自体が不要——並列にしない理由をわざわざ書かない。
3. **ユーザーのコスト・品質指定は表より優先する。**「安く」「軽く」→ 1段下げる。「しっかり」「徹底的に」「深く」→ deep-worker、必要ならWorkflowで検証段を付ける。**下限は quick-worker まで**（ただし対象ファイルが特定済みで本体のコマンド1回で終わるなら委譲しない。それが最安）。**上限は deep-worker**。
4. **既存スキルが該当する作業はスキルが勝つ。** モデル階層へ振る前に、**実在するスキルを確認**し、該当するものがあればそれを使う（内部の重い工程を deep-worker に載せるのは可）。**スキル名を記憶で呼ばない**——スキルは増減する。該当しそうなスキルが実在しなければ振り分け表へフォールバックし、**「あるはずのものが無い」こと自体を欠陥としてHumanへ報告する**（`CLAUDE.md` §2）。
5. **成果物の検証は起草より1段上で。** standard-worker が作った重要成果物の最終確認は deep-worker（またはセッション本体）が行う。
6. **委譲プロンプトには文脈を全て詰める。** サブエージェントは会話を見ていない。前提・制約・期待する出力形式を省略しない。**渡すファイルパスは実在を確認してから渡す**（記憶や推測で書かない。存在しないパスは探索コストと誤読を生む）。ユーザー向けの日本語文面は戻ってきた生データから本体が仕上げる。

## ユーザーへの見せ方

どこへ振ったかを冒頭で一言だけ伝える（例:「検索はquick-worker、検証はdeep-workerに投げます」）。振り分けの講釈はしない。
